# HOOKS — CORE LOGIC LAYER

## OVERVIEW

18 custom hooks (9,716 lines total) forming the application's entire data/communication layer. All Spotify and daemon interaction flows through these hooks.

## ARCHITECTURE PATTERN

Unlike typical React hooks, the large hooks here use **module-level singleton state** with pub/sub:

```
// Module-level globals (shared across all component instances)
let globalWsRef = null;
const subscribers = new Set();

// Pub/sub pattern for cross-component state sharing
export const subscribeXxx = (listener) => { subscribers.add(listener); return () => subscribers.delete(listener); };
export const getXxxState = () => currentState;

// React hook wraps the singleton
export function useXxx() { ... }
```

This pattern exists in `useNocturned.ts`, `useSpotifyData.ts`, `useSpotifyPlayerState.ts`, and `useSpotifyWebSocket.ts`. It avoids React context re-render storms for high-frequency state (WebSocket messages, playback position, BT connection).

## PRESET STORAGE

Hardware preset mappings are stored under `nocturne_presets:<bluetooth-address>` via `src/utils/presetStorage.ts`. The helper owns the one-time migration from legacy global `button{n}Id` / `button{n}Type` / `button{n}Image` / `button{n}Name` / `button{n}Tracks` keys and older `nocturne_button_presets:*` keys; do not access those legacy keys directly in hooks or components.

## CONVENTIONS

- **Standalone exports alongside hooks**: Large hooks export both `useXxx()` hooks and `getXxxState()`/`subscribeXxxState()` standalone functions for use outside React components
- **UUID-correlated requests**: All WebSocket requests use UUID message IDs with pending request maps for response matching
- **Retry with backoff**: Data fetching uses `MAX_RETRIES` + `RETRY_DELAY` constants, WebSocket reconnects use exponential backoff capped at 30s
- **Asynchronous Bluetooth handoffs**: Treat `waiting_for_ios`, `waiting_for_android`, and `waiting_for_macos_connector` as pending success states. They mean the daemon accepted the handoff and is waiting for the platform transport, so the reconnect watchdog must settle instead of immediately issuing another connect request.
- **Bluetooth pairing state**: Normalize canonical `bluetooth.pairing` `event: "paired"` and legacy `type: "pairing_succeeded"` as terminal visual success, and clear cancelled agent prompts. Keep generic `bluetooth.device` `connected` separate from `bluetooth.connection` session establishment so a BLE or baseband link cannot masquerade as iAP2 readiness.
- **Bluetooth discovery leases**: All Nocturne and Mockingbird pairing surfaces acquire the shared discovery coordinator in `useNocturned.ts`. The coordinator serializes transitions, keeps overlapping owners from closing each other, and reapplies the desired state after the daemon WebSocket reconnects. Never send `bluetooth.discoverable` directly from a component or store.
- **Android reconnect:** persist the platform against the active SPP address when Android emits `app.ready`. The UI reconnect singleton requests the daemon's Android wake handoff and treats `waiting_for_android` as pending while the companion reconnects over RFCOMM.
- **Cold-start reconnect presentation:** publish reconnect `pending` state across the initial delay, active request, settle window, and scheduled retry. The app keeps Now Playing mounted while pending, then shows Phone Disconnected when there is no automatic reconnect target or the retry cycle explicitly exhausts. Do not derive this from generic BlueZ connectivity.
- **Ref-heavy patterns**: Callbacks stored in refs to avoid stale closures in event listeners — standard pattern here, don't "simplify" to direct deps
- **Phone volume updates**: `useSpotifyPlayerState.subscribeToPhoneVolume()` publishes normalized 0-100 values from `phone.volume.update`. Subscribers should baseline the first sync, immediately render later phone volume messages including large jumps from volume-button holds, and avoid knob-direction placeholders for phone-media volume.
- **Phone media artwork correlation**: `useSpotifyPlayerState` records optional `media_generation` from each accepted metadata event. Main and Mockingbird artwork consumers accept an image only when both generations match or both are absent. Do not allow a tagged event to pair with an untagged event.
- **Dormant phone sessions**: while actively playing canonical Spotify owns the UI, ignore paused or stopped named media events from another phone app. Android retains historical sessions after apps close. Playing/loading foreign media can take ownership, and pause/stop remains valid after phone media already owns the UI.
- **Cold player state**: Spotify authentication can arrive before the companion emits `app.ready`. The first `spotify.player.state` response may therefore be empty. `useSpotifyPlayerState` performs bounded retries after each monotonic `app.ready` generation and ignores empty warmup responses so it does not erase native phone metadata. Do not gate this on the generic Bluetooth `connected` flag, which can remain false for a healthy iAP2 session.
- **Cold library state**: `useSpotifyData` starts its initial profile and library batch only after the current monotonic `app.ready` generation. The profile response is the warmup probe, malformed required collection envelopes are retried, and failed required batches never publish `initialDataLoaded`. Radio is optional and falls back to its two offline mixes. Fast retries are bounded, followed by a slower same-generation recovery loop. A newer generation cancels the old RPCs before starting its own batch. Mockingbird uses the same parent loader with larger initial playlist, artist, and show limits. Do not weaken this to generic Bluetooth connectivity or cached Spotify auth because both can precede the companion route on a first iOS pairing.
- **Native phone call state**: `usePhoneCalls` consumes only complete daemon snapshots, never sparse platform deltas. Key calls by both `device` and `callId`, query `phone.calls.get` only after Android or iOS `app.ready` establishes a usable phone route, and block duplicate actions until the phone changes or ends the ringing call.
- **Strict Nocturne+ access**: Use `hasStrictNocturnePlusAccess` for phone calls and notification presentation. It requires `entitlementsVerified === true` before accepting an admin grant or an active subscription. Do not substitute `hasPhoneAccess`, which intentionally includes lifetime access for other product surfaces.
